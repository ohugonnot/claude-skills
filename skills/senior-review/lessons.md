# Senior-review — meta-leçons cross-projet (comment piloter la revue)

- **Re-run live d'un reviewer = restaurer propre, zéro backup parasite** : pour vérifier un finding, un reviewer a muté `config.js` (port serveur de test) en faisant ses propres `cp config.js config.js.orig` ; il a restauré le fichier mais laissé les `.orig`/`.bak`, que l'orchestrateur a dû nettoyer. git suit déjà le fichier → muter puis `git checkout -- <file>`, jamais de copie manuelle. Vérifier `git status` propre en fin de revue. — *vu sur 1 run (runs réels)*
- **2ᵉ passe indépendante (senior-review après feature-loop) : valeur prouvée** : sur un module e2e déjà revu une fois par feature-loop, la passe senior-review a trouvé des trous de discriminance ratés au 1er tour (fallback Escape qui ferme un `<dialog>` nativement → test non-discriminant). La review unique sature ; une 2ᵉ passe aveugle, focalisée « ce test rougirait-il vraiment ? », rattrape. Ne pas décourager le multi-passes sur le code qui compte. — *vu sur 1 run (runs réels)*

- **Flag bool propagé en chaîne (handler→source→repo→SQL) : muter chaque COUTURE, pas chaque couche** : les tests par couche peuvent tous être verts (stub handler respecte le flag, intg teste le SQL une fois le flag posé) alors que la transmission entre deux couches est invisible — `HideProcessed: hideProcessed` muté en `false` dans la source survivait à toute la suite unitaire, idem la branche `pageURL` qui re-injecte le flag dans les liens de pagination. Pour tout paramètre traversant N couches, red-check la propagation à chaque jonction. — *vu sur 1 run (runs réels)*
- **Revue de repo entier (URL, pas de diff) : spec-alignment devient docs-alignment, et le receipt le moins cher est la mutation ciblée** : sans ticket, l'oracle de la dimension spec est le README — chaque promesse (seuils, options, plateformes) se vérifie par grep/exec en secondes et rapporte des findings à confiance haute. Pour les gaps de tests allégués, UNE mutation sur un bras de `case` non couvert (suite reste verte → gap prouvé) coûte 30 s et vaut tous les raisonnements. Sur un clone jetable /tmp, la mutation est sans risque pour le working tree de l'user. — *vu sur 1 run (claude-code-statusline, 2026-06-10)*
- **Signature de composant partagé étendue → auditer TOUS les call sites, pas celui de la feature** : ajouter des paramètres (notOrdered/total) à un composant templ réutilisé fait compiler les autres call sites avec des zéros littéraux — la bannière ET le hidden input conditionnels ne s'affichent jamais sur ces chemins, transformant le garde serveur en cul-de-sac 409 sans échappatoire. 3 reviewers l'ont trouvé indépendamment via `grep -rn 'NomDuComposant('` ; le receipt coûte une ligne. Règle : toute extension de signature → grep des call sites + vérifier que chacun peut fournir la vraie donnée (sinon le gap est un finding, pas un détail). — *vu sur 1 run (runs réels)*
- **Routage par clé (sharding/partition/aggregate-id/tenant/topic) : un test qui court-circuite la résolution par clé ne le teste pas — exiger ≥2 entités clés** : trouvé en 2ᵉ passe (sceptique-tests), confirmé par mutation. Un e2e prétendait valider un déblocage cross-vendeur (A ouvre / B clôture / slot de A libéré), mais l'adapter passait UN SEUL agrégat en direct au handler ; or le handler ne gardait que sur `VisitUUID`, le routage par vendeur se faisant au niveau gateway (`AggregateID == SellerEmail`). Le bug ne touchant que l'email, l'assertion d'effet "slot libéré" passait quel que soit le vendeur — seule une assertion d'event intermédiaire l'attrapait. Vérifier aussi que l'assertion d'EFFET final est elle-même discriminante (mutation : bug + assertion intermédiaire neutralisée → doit rougir), pas seulement une pré-assertion sur l'input. Méfiance sur les titres/commentaires de test qui disent "exercises the production wiring". — *vu sur 1 run (runs réels)*

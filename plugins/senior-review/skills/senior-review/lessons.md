# Senior-review — meta-leçons cross-projet (comment piloter la revue)

Leçons sur *comment reviewer* (discriminance des tests, routage par clé, hygiène de mutation…), réutilisables sur d'autres projets. Chargées à l'Étape 1.8, complétées à l'Étape 7.

Format : `- [<dimension>] **<titre>** : <règle actionnable> — *vu sur N runs*`, étiquette obligatoire parmi `spec correctness security design tests perf harness`. Enrichir une leçon existante et incrémenter N plutôt qu'empiler une variante.

> **Instantané publié délibérément.** Ce fichier est une copie curée, promue **à la main** après audit d'anonymisation — le skill ne l'écrit jamais. Sa mémoire de travail vit hors dépôt dans `~/.claude/skill-memory/senior-review-lessons.md` ; c'est elle que lisent l'Étape 1.8 et qu'écrit l'Étape 7. La séparation existe pour qu'aucun run ne publie quoi que ce soit par effet de bord.
>
> ⚠️ **Anonymisation obligatoire avant de promouvoir.** Généraliser chaque leçon : jamais de nom client / vendor / branche, ni de champ, table ou fonction identifiants (« un projet réel », « deux colonnes voisines de même nature »). Ce qui ne peut pas être généralisé ne se promeut pas — ça reste local.

- [design] **Interface multi-impl + champ lu en aval** : quand un consommateur (handler/template) lit DIRECTEMENT des champs de résultat (ex. flags de pagination `HasNext`/`HasPrev`) mais que seules CERTAINES implémentations de l'interface les renseignent, l'implémentation par défaut marche et masque le trou — l'impl non-défaut perd silencieusement la feature. Vérifier que CHAQUE impl d'une interface peuple les champs que le consommateur lit, surtout sur les chemins dégradés/fallback (et les modes de config non-défaut) que les tests ne pilotent jamais. — *vu sur 1 run*
- [correctness] **Le chemin de fallback mérite son propre red-check** : un fallback « best-effort » (ex. source A KO au boot → bascule source B) hérite rarement de la couverture du chemin nominal ; tracer ce que la bascule produit RÉELLEMENT, pas ce que son commentaire promet (« ça marchera quand même » ≠ « avec toutes les features »). — *vu sur 1 run*
- [tests] **Mock à valeur zéro sur le chemin d'erreur = red-check aveugle** : un test qui mocke un appel best-effort en échec avec `Result{}` (zéro-valeur) + une erreur ne peut pas distinguer « l'erreur est bien gérée » de « le check d'erreur est tombé et le code retourne le zéro-valeur par accident » — les deux produisent la même sortie observable. Toujours accompagner le mock d'erreur d'une valeur de succès non-zéro et non-ambiguë (ex. un email factice) sur le même champ que teste l'assertion ; sinon la mutation qui supprime le `if err != nil` ne fait jamais rougir le test. Vérifié par mutation réelle (suppression du check) qui restait verte avant fix, rouge après. — *vu sur 1 run*
- [perf] **Enrichissement coûteux greffé sur une méthode multi-appelants** : quand une fonction déjà partagée par N appelants (`GetByX` générique) gagne un enrichissement (requête DB supplémentaire, appel best-effort) dont un seul appelant a réellement besoin, il fuit sur les N-1 autres (coût + bruit de log) sans bénéfice. Repérable par un grep des call sites de la fonction modifiée avant de juger le placement — si le projet a déjà une convention pour ce cas (méthode séparée appelée à la demande par le seul consommateur), le nouvel enrichissement doit la suivre plutôt que s'ajouter au tronc commun. — *vu sur 1 run*
- [harness] **Branche vendue « test-only » : trianguler par les types de commits d'abord** : avant tout fan-out, `git log base..branch --format='%s'` — des commits `feat:`/`fix:` (migration DB, nouvelle table, alerting) sur une branche promise « refactor/tests only » invalident la promesse en 30 secondes et recadrent toute la revue (chercher les changements assumés, pas seulement les accidents). — *vu sur 1 run*
- [correctness] **Branche longue-vie : collision de numéros de migration = receipt exécutable pas cher** : quand base et branche ajoutent chacune des migrations, comparer les numéros ne suffit pas — parser le dossier migrations avec la lib de migration du projet elle-même (petit main jetable sur le vendored golang-migrate ou équivalent) prouve/réfute le crash au boot en une commande, là où la CI verte trompe (elle ne joue souvent pas les migrations). — *vu sur 1 run*
- [security] **Refacto « extraction de serveur/routes » : reconcilier la table de routes 1:1** : quand un fichier api/routes est éclaté, extraire mécaniquement (méthode, path, middleware) des deux refs et diff — les régressions les plus graves (mTLS/TLSConfig perdu, scope write→read, routes disparues) sont invisibles dans un diff textuel de +5k lignes mais triviales dans une table de 40 lignes. — *vu sur 1 run*
- [tests] **Filet de tests vendu = vérifier qu'il tourne en CI, pas qu'il existe** : des tests DB gated par env var jamais provisionnée en pipeline, ou des fichiers derrière un build tag jamais passé, donnent une CI verte et un filet fictif ; le receipt est `go test` local sans les vars (compter les SKIP) + grep des jobs CI réels. — *vu sur 1 run*
- [correctness] **« Le pipeline saute l'étape aval sur erreur » : tracer la sémantique de retour réelle de l'amont d'abord** : les pipelines résilients retournent souvent `nil` sur erreurs partielles (log + continue) — un early-return aval ne mord alors que sur échec TOTAL, ce qui rétrograde le finding de bloquant à mineur. Receipt = lire le `return` final de la fonction amont, pas le message d'erreur intermédiaire. — *vu sur 1 run*
- [perf] **Chronométrer la migration douteuse sur le dump prod local plutôt que spéculer** : un `EXPLAIN (ANALYZE, BUFFERS)` du SELECT coûteux d'une migration de backfill, joué en lecture seule sur la copie prod, transforme « durée probable en minutes, risque de flapping » en chiffre mesuré en secondes — et change le plan de déploiement. — *vu sur 1 run*
- [correctness] **Rollback binaire post-migration : vérifier `versionExists` de la lib de migration** : golang-migrate (et équivalents) refuse de booter si la version DB dépasse le max des sources embarquées — tout merge qui ajoute une migration rend le revert d'image impossible sans runbook SQL ; à inscrire d'office dans la checklist jour-J d'une revue pré-merge. — *vu sur 1 run*
- [correctness] **Cadence d'ingestion ≠ cadence de consommation sur un dérivé write-once** : quand un pipeline dérivé à watermark (chaque slot écrit une fois, jamais réécrit) consomme une source fetchée MOINS souvent que lui, le forward-fill de la source produit de la donnée dérivée définitivement fausse — pas de la latence rattrapable. Vérifier le couple (fréquence de fetch de chaque source, politique de réécriture du dérivé) ; le receipt est le call-site du fetch dans le scheduler vs celui du dérivé. — *vu sur 1 run*
- [correctness] **Un clamp global dans l'orchestrateur ne protège pas les builders à fenêtre propre** : quand une borne métier (date plancher, inception) est posée sur le from global, grep TOUS les seeds de fenêtre locaux (FirstPoint/LastPoint par entité) — un builder qui calcule son propre pairFrom depuis la donnée brute contourne silencieusement le plancher au bootstrap. — *vu sur 1 run*
- [harness] **Prédictions de mutation du reviewer tests = les exécuter TOUTES, y compris les contrôles positifs** : 2 mutations prédites survivantes + 4 prédites tuées, toutes vérifiées conformes — les contrôles positifs valident que le harnais de mutation mord vraiment, sans eux une « survivante » peut être un harnais cassé. Sur deux runs ultérieurs, des prédites survivantes ont été TUÉES par des tests que le reviewer n'avait pas reliés au symbole (test de cascade ; test de câblage de routes 2 couches au-dessus du switch muté) — la prédiction seule aurait produit des faux positifs « important ». — *vu sur 3 runs*
- [harness] **La passe fresh-eyes post-fixes trouve une COUCHE différente de bugs** : sur un même diff, la première passe (ancrée sur les formules/le delta du jour) a validé les maths mais raté deux bloquants de CYCLE DE VIE (seed cold-start daté avant l'existence des données ; forward-fill dépendant d'un état en mémoire qui ne survit pas entre les runs cron). Les reviewers frais, non primés par les zones retravaillées, tracent les seeds et les watermarks. Une passe œil-neuf complète après les fixes n'est pas une redondance — c'est un autre angle. — *vu sur 1 run*
- [correctness] **Rejouer chaque chemin d'écriture incrémental en mode « un slot par run »** : un pipeline cron qui traite un slot à la fois casse les invariants conçus en mode batch (prev/forward-fill vides au démarrage de chaque run, fenêtres partielles, watermark global vs par-entité). Question systématique : « que se passe-t-il quand cette boucle ne fait QU'UNE itération, à froid, puis repart ? » — *vu sur 1 run*
- [tests] **Exiger le smoke live sur l'API réelle avant le verdict final** : mocks et httptest valident le contrat supposé, pas le contrat réel ; un test opt-in guardé (env var, 1 crédit API) contre l'API de prod + la vraie DB coûte une minute et transforme « ça devrait marcher » en « 126 barres réelles stockées et consommées ». — *vu sur 1 run*
- [correctness] **Le fallback « point par point » sur une transaction avortée est un mensonge structurel** : après un échec d'INSERT dans une tx Postgres, TOUT retry sur la même tx échoue en 25P02 — un helper « partial success » sans SAVEPOINT ne peut jamais réussir partiellement. Receipt en une commande : seed un doublon, appeler le helper avec [dup, valide, valide], compter les rows. — *vu sur 1 run*
- [harness] **Le receipt exécuté recalibre la sévérité dans les deux sens** : un « bloquant » théorique (perte de batch) s'est révélé auto-guérissant au run suivant (le commit échoue → watermark non avancé) — l'exécution a transformé un bloquant allégué en important prouvé, avec le mécanisme exact de récupération documenté. Toujours exécuter le scénario avant d'arbitrer la sévérité d'un finding transactionnel. — *vu sur 1 run*
- [correctness] **La lentille « sémantique des données persistées, champ par champ » trouve ce que correctness/spec ratent** : tracer CHAQUE colonne écrite (qui la pose, sur chaque chemin d'écriture, qui la lira) a attrapé un champ identitaire vide sur un seul des 5 chemins — invisible aux passes formules/cycle de vie car sans effet sur les valeurs calculées. — *vu sur 1 run*
- [correctness] **Fix de classe appliqué à N-1 des N sites homologues** : quand une famille de builders/consommateurs homologues a reçu un fix pour une classe de bug (ex. seed lookback avant la fenêtre sur un dérivé write-once), grep le pattern du fix et vérifier CHAQUE site homologue — le refuteur le plus utile est celui qui cherche le « mécanisme jumeau » déjà corrigé ailleurs : sa présence prouve que la classe de bug est réelle et que le site non porté est un oubli, pas un choix. — *vu sur 1 run*
- [correctness] **Fenêtre [watermark+step, now] = forward-fill structurellement aveugle** : un consommateur qui interroge sa source sur une fenêtre commençant juste APRÈS sa dernière donnée ne peut jamais voir la valeur-seed d'avant la fenêtre ; tout forward-fill purement intra-fenêtre est donc mort au premier trou qui précède la fenêtre (week-end, jour férié, source en panne). Receipt en un test : mock la source vide sur la fenêtre, asserter que le résultat n'est pas vide. — *vu sur 1 run*
- [harness] **Baseline de bruit re-mesurée ENTRE les mutations** : des E2E time-of-day dépendants peuvent commencer à rougir en cours de session (l'horloge avance) et polluer les verdicts kill/survive ; dès qu'un test inattendu rougit sous mutation, rejouer immédiatement la suite NON mutée et n'attribuer à la mutation que le delta vs cette baseline fraîche. — *vu sur 1 run*
- [tests] **Tests-miroir : grep les symboles du SUT dans le fichier de test** : un test qui « teste la logique en isolation » en la RÉ-IMPLÉMENTANT (boucle forward-fill locale, division 1/x à la main) reste vert pour toujours quel que soit le code de prod ; receipt en une commande — grep des fonctions de prod censées être couvertes dans le fichier de test, zéro occurrence = test décoratif. — *vu sur 1 run*
- [correctness] **Job cron chaîné + I/O non-annulable = gel du pipeline entier** : `SkipIfStillRunning` (robfig/cron et équivalents) ne tue jamais le job en cours — il saute les ticks suivants. Toute boucle réseau dont la terminaison dépend de la bonne foi du serveur (pagination pilotée par les dates de la réponse, sleeps bruts sans ctx) transforme un vendor buggé en gel silencieux et illimité de tout ce qui partage la chaîne ; vérifier cap d'itérations + progression monotone + ctx threadé jusqu'au transport. — *vu sur 1 run*
- [harness] **Le refute-panel filtre mieux que la sévérité initiale** : sur 5 findings med-confidence envoyés au panel, 2 tenaient, 2 tenaient partiellement (sous-claims fausses éliminées), 1 est tombé entièrement (chaîne causale brisée en 3 maillons) — le coût du panel (~1/3 des tokens reviewers) a évité un faux bloquant et recalibré deux sévérités ; réserver le panel au douteux/critique reste le bon ratio. — *vu sur 1 run*
- [correctness] **Plafond global vs granularité par-entité sur un dérivé write-once** : quand un pipeline dérivé calcule son plafond de fenêtre depuis le MAX(timestamp) GLOBAL des sources alors que chaque source avance indépendamment (sync résilient par-entité), chaque retard d'une entité devient de la donnée FABRIQUÉE à son slot le plus frais, scellée par le watermark. Receipt en 2 lectures : la requête du plafond (filtre par-entité ou global ?) et la branche gap-fill du builder. La granularité du plafond doit égaler la granularité d'avancement des sources. — *vu sur 1 run*
- [correctness] **Entrée absente ≠ entrée vide dans une map de sources** : quand la couche source MATÉRIALISE ses vrais vides (rows plates volume 0), une branche gap-fill déclenchée sur « absent de la map » confond « vide confirmé » et « pas encore arrivé ». Router la décision de fill sur présence-avec-zéro, jamais sur absence — l'absence doit stopper sans avancer le watermark. — *vu sur 1 run*
- [harness] **Working tree mouvant pendant la revue : ancrer les reviewers sur `git show HEAD:`** : si l'utilisateur édite en live pendant le fan-out, les findings anchorés sur le working tree deviennent invérifiables (lignes décalées, code disparu). Consigne à donner d'office aux reviewers quand la cible est un état commité ; à la synthèse, re-vérifier chaque finding contre le working tree courant (certains seront déjà corrigés par l'utilisateur — les rapporter comme tels, pas comme actifs). — *vu sur 1 run*
- [correctness] **Un fix anti-fabrication au tail peut surcorriger un trou interne** : remplacer un forward-fill « fabrique-sur-absence » par un `break`/stop corrige le cas TAIL (données pas encore arrivées) mais casse le cas TROU INTERNE (données présentes après le trou) — le stop perd tout le post-trou et fige le watermark. Les deux cas se présentent identiquement (source vide + prev non-nul) ; seul un `lastDataT` (dernier slot ayant réellement de la donnée) les distingue. Receipt décisif : construire une série avec un trou interne (data / hole / data) et asserter que le post-trou est bien produit. — *vu sur 1 run*
- [tests] **Un test de garde placé sur la DERNIÈRE itération de boucle ne pince pas break vs continue** : si le slot déclencheur est à `globalTo` (dernière itération), `break` et `continue` sont observablement identiques — le test passe quel que soit le mot-clé. Toujours placer le déclencheur AVANT la fin de la plage, avec des données valides au-delà, pour qu'une mutation break→continue rougisse. Vérifiable par mutation directe des 3 sites → suite verte = tests vacants. — *vu sur 1 run*
- [harness] **Passe de clôture qui audite le fix de la passe précédente = angle à part entière** : demander explicitement aux reviewers frais de tracer le BLAST RADIUS du dernier correctif (pas de le re-valider) fait émerger la surcorrection que les passes qui l'ont produit ne voient pas. Ici 3 dimensions indépendantes (correctness, lifecycle, tests) + refuteur ont convergé sur la même subtilité d'un fix de 3 lignes. — *vu sur 1 run*
- [tests] **Tests de câblage : l'attribut sécurité, pas la présence** : un test de table de routes qui n'asserte que l'existence des paths (`map[path]bool`) vaut ~zéro — il reste vert sur un downgrade de scope authz, un flip GET↔POST ou un middleware droppé ; sur un projet réel la classe de régression exacte (write→read) s'était produite pendant la refacto et seule la review l'avait vue. Receipt en un grep : si la boucle sur `Routes()` ne lit jamais `route.Method` ni le middleware, le test est décoratif — exiger le table-driven (method, path, scope). — *vu sur 1 run*
- [harness] **Passe de convergence = changer la coupe, pas relire** : après une passe par composant, découper la suivante par méthode orthogonale (comptabilité de symboles disparus, threat-model dédié, outillage opérateur, discriminance de suite) ; sur un projet réel la passe orthogonale n'a RE-trouvé aucun finding corrigé (signal de convergence objectif) mais a sorti des classes neuves invisibles à la coupe précédente (faux-verdict d'un script de comparaison, vacances de couverture). — *vu sur 1 run*
- [harness] **Comptabilité de symboles = falsificateur de messages de commit** : énumérer les funcs disparues base→HEAD et classer (renommée/inlinée/morte/perdue-avec-appelants) est mécanique, exhaustif, et vérifie à peu de frais les claims des commits (« X merged into Y » réfutable en lisant Y) ; le file-by-file rate les capacités CLI/env-vars droppées que cette coupe attrape. — *vu sur 1 run*
- [correctness] **Script de comparaison : chaque count calculé doit entrer dans le verdict** : le pattern faux-PERFECT = un outil qui CALCULE `missing` mais ne le met pas dans le CASE de décision, et dont le GROUP BY porte sur la table rebuilt (une entité totalement absente ne produit aucune ligne). Receipt en un grep du CASE : tout count affiché mais absent de la décision est un trou de verdict. — *vu sur 1 run*
- [correctness] **Une couverture prouvée par un `lastX` doit couvrir TOUTES les dépendances du prédicat, pas seulement la principale** : un garde qui décide « attendre vs fabriquer » à partir d'un `lastDataT` calculé sur les entrées SOURCE peut se tromper quand la même conversion dépend AUSSI d'entrées TAUX/annexes non incluses dans le calcul. Vérifier que le prédicat de complétude couvre chaque entrée que le consommateur (ici convertPrice) exige. Souvent near-unreachable (l'entrée annexe est forward-fillée/profonde) mais l'asymétrie est réelle — le tester ou la documenter. — *vu sur 1 run*
- [harness] **Refuter son propre fix via un agent indépendant quand on est l'auteur** : quand l'orchestrateur downgrade un finding qui porte sur SON propre correctif, le self-preference bias joue à plein. Mandater un refuteur indépendant en lui disant explicitement « l'orchestrateur a un conflit d'intérêt, refais les receipts » — il a ici confirmé le downgrade par des probes propres (immunité usd forward-fill, tradeoff produit), ce qui vaut bien plus que l'auto-évaluation. — *vu sur 1 run*
- [tests] **Un fix de deadlock/concurrence livré sans test de régression est un 🟡 même quand le code est correct** : la correction du sender (retrait d'un bail-out ctx.Done qui bloquait le receiver) était juste, mais zéro test l'ancre — une réintroduction future passerait inaperçue. Le finding « pas de test sur le fix concurrent » est actionnable et durable indépendamment de la correction du code. — *vu sur 1 run*
- [harness] **Les choix d'apparence délibérés doivent entrer au context pack** : une asymétrie visuelle assumée (champ image volontairement vide sur certaines valeurs, convention "pas de vignette pour les binaires purs") est indistinguable d'un oubli pour un reviewer aveugle — si le pack ne liste pas ces décisions, le reviewer spec-alignment les flague en gap et coûte un cycle de réfutation. — *vu sur 1 run*
- [tests] **Un champ réutilisé pour deux sémantiques (chemin OU couleur CSS) piège les tests d'existence de fichiers** : avant d'écrire un test "toutes les références existent sur disque", inventorier les valeurs réelles du champ (grep des préfixes) — un champ image peut porter des hex colors, des URLs ou des chemins selon l'option. — *vu sur 1 run*
- [harness] **« Impact prod » d'un reviewer → vérifier le flag d'activation avant de calibrer** : un finding sur un produit/feature derrière un flag (RunLevel, NotProd, feature-flag) hérite de la sévérité du flag, pas du chemin de code ; deux reviewers indépendants ont qualifié « prod » un produit `NotProd: true` — le receipt tenait en un grep du flag dans la config produit. L'orchestrateur doit faire ce grep systématiquement sur tout finding prod-facing. — *vu sur 1 run*
- [correctness] **« Skip empty values » sur un type optionnel ne couvre souvent que le nil, pas la chaîne vide** : un garde `else { continue }` en bout de chaîne if/else de conversion laisse passer `ptr("")` (String non-nil → valueStr="" → envoyé). Receipt : lire l'ordre exact conversion→skip, puis probe d'exécution sur un défaut `ref("")`. Classe générale : nil ≠ zero-value dans les gardes d'omission. — *vu sur 1 run*
- [tests] **Tests d'un garde-fou écrits depuis l'état DÉFAUT deviennent vacuous quand le défaut change dans le même diff** : si le test attend « X forcé à 0 » et que le défaut est devenu 0 dans le même lot, la mutation `if false &&` du garde reste verte. Red-check : désactiver le bloc gardé et exiger le rouge ; fix : poser un état non-défaut AVANT d'exercer le garde. — *vu sur 1 run*
- [tests] **Dans un moteur preset+guérison, la convergence du heal masque les presets aux tests d'état** : muter la valeur d'un preset peut rester vert si la guérison (findAvailableDefault sur matrice When) reconverge vers la même unique valeur disponible — l'assertion d'état observable ne discrimine pas le mécanisme. Quand une seule valeur est disponible, le fix honnête est un commentaire « preset actuellement redondant avec la matrice When », pas un test impossible. — *vu sur 1 run*
- [harness] **Un réfuteur mandaté peut AGGRAVER le dossier, pas seulement le démonter** : sur un finding déjà convergent (3 reviewers), le skeptique chargé de le réfuter a découvert une pièce que personne n'avait vue (un hook pre-commit qui exécutait la suite par défaut, transformant « test réseau non gated » en « appel API partenaire à chaque commit + commit bloqué si réseau KO ») et a réfuté l'hypothèse « délibéré » via la doc du projet lui-même. Formuler le mandat du réfuteur avec des contre-hypothèses OUVERTES (délibéré ? skip effectif ? sévérité ?) plutôt que binaire vrai/faux — la passe de réfutation est aussi une passe d'approfondissement. — *vu sur 1 run*
- [harness] **Re-review complète vs contrôle du delta : les corrections écrites par l'orchestrateur sont le delta le plus risqué** : quand l'utilisateur demande « faut-il repasser une review complète ? », vérifier d'abord d'où venaient les trouvailles de la dernière passe — si elles sortaient toutes de zones alors non couvertes et qu'il n'en reste plus, une passe fresh relit du déjà-fouillé (rendement ~nul). Le vrai résidu est le delta non re-vérifié par un tiers, et en particulier les corrections rédigées par l'orchestrateur lui-même (self-review sans receipt) : sur un run réel, la SEULE erreur résiduelle (terme métier faux dans un mail fournisseur) venait d'une correction de l'orchestrateur, attrapée par une continuation ciblée du reviewer d'origine (~10× moins cher qu'une passe complète). Après ça, pointer vers les oracles EXTERNES restants (contrat partenaire, envoi réel) plutôt qu'une passe LLM de plus. — *vu sur 1 run*
- [harness] **Brief de mutation à un subagent sur un working tree porteur d'éditions non commitées : interdire git checkout DANS le brief** : le piège du workflow hybride (checkout global qui efface le fix avec la mutation) se déclenche aussi via un reviewer délégué si son brief dit « restaure via git checkout » ; le brief doit imposer la restauration par snapshot-copie (cp hors repo, md5 avant/après), et l'orchestrateur snapshotte lui-même le fichier AVANT de lancer le fan-out — correction en vol par SendMessage possible mais c'est une course. Le piège mord AUSSI l'orchestrateur en direct : sur un run réel il a exécuté ses propres mutations sur un FIX NON COMMITTÉ et le `git checkout --` de restauration a effacé le fix entier (re-écrit de mémoire, receipts à refaire). Règle absolue : dès que la base d'une mutation contient du travail non committé, snapshot-cp AVANT la première mutation, et git checkout est INTERDIT comme mécanisme de restauration. — *vu sur 2 runs*
- [correctness] **Backfill et chemin live d'une table à clé composite : vérifier colonne par colonne que la clé vient de la MÊME source sémantique** : un backfill SQL qui dérive une colonne de clé d'un champ historique de la table pendant que le chemin live la dérive de la config produit des lignes invisibles aux lectures (clé désalignée) — la feature marche en live, est inerte sur tout l'historique backfillé, et aucun test ne le voit si les tests seedent la table directement (en contournant le backfill). Receipt en 3 greps : la colonne dans l'INSERT du backfill, dans l'INSERT live, dans le WHERE de lecture ; exiger un test round-trip backfill→lecture. — *vu sur 1 run*
- [tests] **Test de wiring AST « le defer existe » : la présence ne prouve pas l'ordre d'armement** : un test qui parse l'AST pour vérifier qu'un `defer recoverHandler()` existe dans la fonction reste vert si du code paniquant est inséré AVANT le defer (recover jamais armé → crash process réel). Receipt exécuté : injecter un déréférencement nil avant le defer, relancer le test — PASS = test décoratif. Le vrai test appelle la fonction avec une dépendance mockée qui panique et vérifie l'absence de crash. — *vu sur 1 run*

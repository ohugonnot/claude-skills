# spec

- **spec-alignment** : le diff couvre-t-il TOUT le ticket (chemins, critères d'acceptation) ? gaps non implémentés ? scope creep (modifs hors ticket) ? **Décisions non spécifiées** : lister les choix que l'implémentation a faits et que le ticket ne précisait pas (bibliothèque, style de gestion d'erreurs, emplacement d'un fichier, nom d'une API publique, format). Ce sont ceux qu'on découvre en production.
  **« Conforme à l'existant » n'est pas un verdict quand le ticket se plaint de l'existant.** Un ticket qui dit « aujourd'hui c'est trois étapes », « le vendeur repart de zéro », « on perd la donnée » énonce une mesure à améliorer. Le flux neuf se juge alors contre CETTE plainte (nombre d'étapes, de clics, culs-de-sac, ressaisies), jamais contre le flux voisin. Absoudre un parcours parce que son voisin fait pareil est le mode d'échec le plus coûteux de cette dimension : il passe toutes les autres coupes, et c'est l'utilisateur final qui le trouve en trente secondes. Recompter explicitement les étapes du parcours livré et les comparer au chiffre du ticket.

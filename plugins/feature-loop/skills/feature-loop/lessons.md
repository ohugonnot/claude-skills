# Feature-loop — meta-leçons cross-projet

Leçons sur *comment piloter la boucle*, valables sur tous les projets (pas les specs d'un projet — ça va dans `project_feature_loop_insights.md`). Chargé à l'init, complété en fin de run et par `learn`.

Format : `- **<titre>** : <règle actionnable> — *vu sur un run réel*`. Additif uniquement.

## Leçons

- **Re-dériver la preuve d'un devil's advocate qui dit "SURVIVES", ne jamais la croire sur sa confidence** : un juge adversarial peut rejeter (haute confiance 0.85) un finding réel du reviewer principal via une preuve mathématique dont le LEMME est faux. Vu sur un-projet #143 (review-only) : C2 a "prouvé" que typical∈[low,high] en supposant typical_route∈[low_route,high_route] — faux, car la conversion à bases de taux mixtes (Close×rate.Close vs High×rateTypical) sort Close€ de la bande. La mère doit re-dériver le lemme contre le code réel quand un DA contredit le reviewer sur un axe invariant/sécurité, pas arbitrer sur les confidences. — *vu sur 1 run (143-projet-prix)*
- **Désaccord MAJOR-vs-none entre reviewer et devil's advocate = arbitrage par lecture directe du code + magnitude empirique, pas panel** : quand le point est purement technique et vérifiable (une formule, un clamp), la mère tranche plus vite et plus sûrement en lisant les 50 lignes concernées qu'en montant un panel-3. Réserver le panel aux jugements non re-dérivables. — *vu sur 1 run (143-projet-prix)*
- **Pagination : red-check la frontière exacte, pas que la page partielle** : un test de "dernière page" qui n'utilise qu'une dernière page PARTIELLE (`total < offset+pageSize`) ne distingue pas `HasNext: total > offset+pageSize` de `>=` — ils ne diffèrent qu'à `total == offset+pageSize` (dernière page PLEINE). Toujours un cas exact-boundary. — *vu sur compositeSource un projet réel (mutation `>`→`>=` survivait en vert)*
- **Dédup ⨉ pagination sur 2 sources : la fusion fenêtrée naïve est fausse** : retirer un doublon décale la fenêtre au-delà de ce qu'on a fetché de chaque source. À petit volume, full-fetch + merge/dedup/paginate en mémoire est la solution simple *correcte* (cap + warn anti-troncature-silencieuse). — *vu sur compositeSource*
- **Test-writer ∥ reviewer = review sur état périmé** : lancer l'agent de tests et le reviewer aveugle EN PARALLÈLE fait que le reviewer note "Tests=0/bloquant" alors que les tests arrivent en même temps. Séquencer tests AVANT review, OU prévenir le reviewer que des tests sont ajoutés concurremment (sinon un faux major Tests). — *vu sur supplier login (review Opus Tests=4 alors que 14 tests ajoutés en //)*
- **`make generate` "0 updates" ≠ pas régénéré** : le lock `.makegenerate.lock` peut afficher 0 updates ; vérifier que le `*_templ.go` contient bien le nouveau markup (grep) avant de croire le templ à jour. — *vu sur supplier portal*
- **[SUPERSEDED — règle raffinée en SKILL §4.5b : `git checkout --` si fichier propre/committé, restauration par chaîne exacte si modifs non commitées ; jamais `cp` (mauvais cwd = fichier resté muté, vu 8.3.2)]** ~~Red-check : restaurer par copie de fichier, jamais `git checkout -- <file>`~~ : en mode in-place avec impl non commitée, `git checkout --` restaure HEAD = efface l'implémentation entière du fichier, pas seulement la mutation. — *vu sur 1 run (un-site, mono)*
- **Reviewer qui généralise un finding par symétrie ("X a le bug donc Y aussi") : vérifier chaque cible séparément** : sur un-site le reviewer a étendu un vrai finding (benchmark.js, units minute réels) à un-module.js qui n'a PAS de vue intraday — moitié vrai, moitié halluciné. — *vu sur 1 run*
- **Red-check sur fichier porteur de modifs non commitées : restauration par chaîne exacte, JAMAIS `git checkout -- <file>`** : le checkout restaure HEAD et efface le travail non commité du même fichier (vécu : un refactor de la même session effacé, FAIL silencieux en aval). Muter via remplacement de chaîne unique et restaurer en réécrivant le contenu original gardé en mémoire. — *vu sur 2 runs (sender-un-client-fixes, strict-sequential-resolve)*
- **Vérifier la SÉMANTIQUE d'un champ tiers sur des artefacts réels (XML/dumps) AVANT d'implémenter, pas sur le nom du champ** : un champ nommé "OrderClientId" (option un-client 9001) a été pris pour "id client" ; les 4 XML réels du fournisseur montraient « un champ tiers » = numéro de COMMANDE (préfixe magasin + compteur), le client étant dans un autre champ. Le run a implémenté 2 itérations sur la mauvaise cible avant que l'user demande de regarder les XML. Leçon : pour tout mapping vers une API tierce, exiger un exemple réel (dump/XML) en INPUT du plan, et y lire la valeur effective de chaque champ — le nom ment. — *vu sur 1 run (202-un-client-9001)*
- **DB dev partagée entre worktrees = piège schéma-en-avance au smoke live** : un autre worktree (#203) a migré la DB commune en v56 pendant le run #202 ; le serveur frais #202 (sans cette migration) refuse de démarrer (golang-migrate « no migration found for version 56 »). Fix non destructif : copier temporairement (non-commité) le fichier de migration de l'autre branche dans migrations/ (go:embed le ré-embarque au `go run`), lancer le smoke, retirer. Ne PAS surgery le schema_migrations partagé. — *vu sur 1 run (202-un-client-9001)*
- **La baseline preflight doit lancer la MÊME suite que le gate (tags intg inclus)** : un échec préexistant découvert seulement au gate force un stash/unstash de diagnostic en pleine boucle (et un `git stash` sans `-u` laisse les tests untracked qui cassent la compile — toujours `-u`). — *vu sur 1 run (runs réels)*
- **Serveur lancé en arrière-plan : sortie vers fichier direct, jamais `| head`/pipe** : les logs restent piégés dans le buffer du pipe tant que le process vit → diagnostic aveugle (17 min perdues sur un bind-retry silencieux qu'une ligne de log montrait dès la 10e seconde). — *vu sur 1 run (runs réels)*
- **Un `//nolint` posé par l'agent d'impl doit être vérifié contre le linter qui FIRE réellement, pas cru sur parole** : sur un projet réel, l'agent A a ajouté `//nolint:goerr113` sur des `fmt.Errorf` capitalisés — or goerr113 n'était PAS activé (config = revive), et le vrai flag était `revive:error-strings` (message d'erreur capitalisé/ponctué). Le nolint suppressait un linter inexistant → warning « unknown linter » + l'erreur réelle restait. La mère DOIT lancer le vrai golangci-lint et lire la règle qui fire avant de faire confiance à un nolint. Fix propre ici : un type `T string` implémentant `error` (échappe à error-strings car pas un littéral errors.New/fmt.Errorf) plutôt que suppresser. — *vu sur 1 run (runs réels)*
- **DA « major » sur replay/idempotence d'un event handler ES → re-dériver, souvent minor** : le devil's advocate a classé « ghost-toast au replay » en major. Arbitrage par lecture code : (a) le replay ne produit un toast que si un subscriber SSE est live sur la visite HISTORIQUE pendant le rattrapage (quasi-nul) ; (b) le chemin nominal (toast succès) avait DÉJÀ ce comportement pré-existant — le diff n'introduit pas une nouvelle classe de bug. → minor. Le fix reste cheap et correct (guard `ErrOrderAlreadyExists → return nil` avant les notifs), donc appliqué en iter-2, mais sans bloquer. Règle : un finding replay/idempotence se re-dérive contre « subscriber live au moment du replay ? » ET « le chemin nominal a-t-il déjà ce comportement ? ». — *vu sur 1 run (runs réels)*
- **Garde de périmètre sur l'agent d'impl : `git diff --name-only` post-impl vs scope déclaré** : sur une tâche e2e « test-only / ne pas toucher prod », l'agent A a modifié un `.templ` de prod de sa propre initiative pour rendre la prémisse d'un test vraie (rendre un `data-no-enter-submit` présent). Rattrapé en review, mais coûteux. Un `git diff --name-only` confronté au scope (surtout prod sur tâche test-only) le détecte instantanément, avant le gate. — *vu sur 1 run (runs réels)*
- **Discriminance d'un test > red-check mono-mutation** : un test critique peut passer pour la MAUVAISE raison quand (a) deux défenses se recouvrent (« ceinture+bretelles » : `data-no-submit` form + `data-no-enter-submit` input → retirer un seul ne change rien d'observable) ou (b) la plateforme couvre nativement (un `<dialog>` HTML ferme sur Escape sans aucun JS → un test qui ferme via Escape passe même si le handler app.js est cassé). Avant de croire un test « non-vacant », vérifier qu'il cible le mécanisme SPÉCIFIQUE et qu'aucun chemin redondant/natif ne le ferait passer ; sinon re-cibler (ex: tester `data-href` qui n'a aucun fallback natif). — *vu sur 1 run (runs réels)*
- **Livrable = code de test → la séparation writer≠tester s'effondre** : pas de « test du test ». Agent A écrit les tests, agent B ne s'applique pas, le signal externe = gate live + red-check (muter la vraie chose testée), l'invariant qui reste = reviewer≠writer. Ne pas spawner de méta-test (faux confort). — *vu sur 1 run (runs réels)*
- **Table à lignes créées paresseusement : exiger un test SANS seed sur toute écriture indépendante** : quand une feature ajoute une colonne écrite par un chemin distinct du flux qui crée la ligne (ici `supplier_tracking` : ligne créée seulement au save note/ETA, mais `processed_at` écrit par un autre handler), un `UPDATE ... WHERE clé` no-ope silencieusement sur clé inexistante (0 ligne, pas d'erreur) = perte de donnée invisible. L'intg qui seede toujours la ligne MASQUE le bug. Le reviewer Opus l'a attrapé en notant que l'INSERT n'existait que dans l'autre chemin. Règle : imposer à l'agent B un cas « écriture sur clé vierge prouve la création » (rougit sur UPDATE nu, vert sur UPSERT). — *vu sur 1 run (runs réels)*
- **Unicité générée en batch : le check DB ne voit pas les entités non flushées** : tout générateur de valeur unique (cote, code, slug…) appelé en lot (import par batch, fixtures à flush unique) doit tenir un registre mémoire des valeurs assignées non flushées — sinon doublon → violation d'index au flush, parfois avalée par le catch du lot (perte silencieuse). Le test qui le prouve : 2 assignations SANS flush intermédiaire puis flush unique. — *vu sur 1 run (un-catalogue, Symfony/Doctrine — 2 bloquants attrapés en review)*
- **Sémantique des assertions de framework de test : vérifier sur UN run avant d'en dépendre** : `assertEmailCount` (Symfony) compte PAR-REQUÊTE même avec `disableReboot()` (services resetter) — un test multi-soumissions qui suppose l'accumulation échoue en CI. Généralisable : toute assertion d'accumulation (mails, events, logs) a une sémantique de reset à vérifier empiriquement. — *vu sur 1 run (inscription honeypot/rate-limit)*
- **Scanner de secrets CI : il flagge le PATTERN d'affectation et scanne CHAQUE commit de la branche** : `$password = '…'` dans un test = flag GitGuardian ; le même littéral inline dans un tableau passe. Corriger ne suffit pas : squasher la branche (`reset --soft` sur merge-base + commit unique + `push --force-with-lease`) pour purger l'historique de la PR. — *vu sur 1 run (échec CI ×2 avant le squash)*
- **Gate = CI distante (pas de runtime local) : red-check en 1 commit groupé, discriminance lue dans la liste exacte des tests échoués, squash final** : quand chaque exécution de tests coûte un run CI (~4 min), grouper les 3-5 mutations red-check en UN commit honnêtement nommé (« mutations TEMPORAIRES volontaires — sera reverté »), attendre UN run rouge, vérifier que les échecs = exactement les tests ciblés (627 tests / 2 failures = 2 cibles → discriminance prouvée), restaurer, puis squasher la branche (purge aussi l'historique pour les scanners type GitGuardian). Un message de commit qui déguise la mutation en « test work » se fait refuser par les garde-fous — l'honnêteté du message fait partie du mécanisme. — *vu sur 1 run (export-fixtures-21, mouvement-municipal, vendor absent localement)*
- **Idempotence octet-pour-octet à travers une colonne JSON(B) : trier les clés à l'export** : PostgreSQL jsonb réordonne les clés (longueur puis ordre binaire) → export → import → export diffère alors que les données sont identiques. Tout exporteur visant un critère « JSON identique » doit ksort récursivement les champs issus de colonnes json/jsonb, et le test d'égalité d'entité doit comparer canoniquement. — *vu sur 1 run (export-fixtures-21, échec CI piégeux)*
- **Round-trip d'un upsert : tester le chemin UPDATE, pas seulement le CREATE à neuf** : un test round-trip qui recrée l'entité depuis une base vidée ne détecte pas un champ jamais réappliqué sur entité EXISTANTE (vu : position de contribution skippée si (person,role) matche — le scénario réel du boot Docker est l'upsert, pas la création). Exiger un test « entité préexistante + valeur modifiée dans la source → la valeur est réappliquée » pour chaque champ éditable. — *vu sur 1 run (major attrapé par review Opus, invisible aux tests create-only)*
- **« EM fermé » ne bloque que persist/flush/remove — réfuter par probe avant d'accepter un critical "EntityManager is closed"** : un reviewer a classé critical « catch UniqueConstraintViolation → EM fermé → re-render d'un form à EntityType = 2ᵉ 500 ». Probe KernelTestCase (form soumis, `$em->close()`, `createView()` + SELECT DQL) : tout passe — Doctrine n'appelle `errorIfClosed()` que sur persist/flush/remove. 10 lignes de probe tranchent mieux et plus vite qu'un panel ; même famille que « re-dériver le lemme d'un DA ». — *vu sur 1 run (57-admin-forms, Symfony)*
- **Tests de normalisation (trim/casse) via soumission de form Symfony = non-discriminants** : TextType trime nativement (`trim: true` défaut) → muter le trim du setter d'entité laisse la suite verte (défense native plateforme + redondance form-event). Le test discriminant est UNITAIRE sur le setter ; il protège en réalité les chemins hors form (imports, fixtures). Généralisation du pattern « défense native » (dialog/Escape) aux normalisations d'entrée. — *vu sur 1 run (57-admin-forms)*
- **Smoke live UI : afficher ≠ exercer — soumettre le form, cliquer les nouveaux contrôles, vérifier l'effet en DB** : un smoke qui navigue + screenshot des pages en 200 ne prouve RIEN sur le chemin d'écriture. Sur 59-admin-utilisateurs, le smoke « visuel » a validé une page dont la checkbox était morte (CSS `appearance:none` global), le bouton Modifier absent (flag `with_new_btn` mal réutilisé dans le template partagé) et la migration non appliquée à la DB dev — les 3 attrapés par l'USER en cliquant. Checklist smoke-live UI : (1) appliquer les migrations sur la DB runtime AVANT, (2) soumettre réellement chaque form nouveau/modifié, (3) cliquer chaque contrôle nouveau, (4) vérifier l'effet en DB ou sur la page suivante. Premier consommateur d'un flag de template partagé = exposeur de bugs latents : l'interaction réelle est le seul filet. — *vu sur 1 run (59-admin-utilisateurs, mouvement-municipal)*
- **Toute route nouvelle doit être atteignable par navigation — la review code-centrique ne le voit pas** : une page créée + testée + smokée peut rester ORPHELINE (aucun lien entrant dans l'UI) ; ni l'agent A, ni l'agent B, ni le reviewer ne posent la question « comment l'utilisateur arrive ici ? ». Ajouter au plan ET à la review : pour chaque route ajoutée, citer le lien entrant (template + ligne) ; s'il n'existe pas, c'est un finding. — *vu sur 1 run (59-admin-utilisateurs : page /activite sans lien entrant, demandée par l'user)*
- **e2e fonctionnel valide la PRÉSENCE DOM, pas le LAYOUT — le smoke live UI doit comparer le rendu réel** : sur 55-admin-selecteurs, un e2e à 9/9 vert vérifiait que `.collection-item-inline` EXISTE sur une ligne ajoutée dynamiquement, mais pas que rôle+position étaient côte à côte (`getBoundingClientRect().width` 126 vs 236 empilé) — l'user a trouvé le bug de layout en cliquant. Pareil pour la position des tags (au-dessus vs sous la recherche). Pour une feature UI, le smoke live doit comparer le LAYOUT (bounding boxes, screenshot, 1re vs Nième occurrence d'un composant répété), pas seulement asserter la présence des nœuds. L'usage réel reste le juge ultime du rendu. — *vu sur 1 run (55-admin-selecteurs : 3 bugs UI trouvés par l'user en live, ratés par review code + e2e fonctionnel)*
- **Reconstruire un prototype Symfony CollectionType en JS : `ctrl.closest('div')`, jamais `div:has([name])`** : `div:has([name*="[champ]"])` matche le wrapper EXTERNE du prototype (qui contient tous les champs) → les form_row de chaque champ pointent le même nœud → markup cassé. Et `form_widget(collection.vars.prototype)` rend le markup PAR DÉFAUT, pas la structure custom de la boucle `{% for %}` du template : une ligne ajoutée dynamiquement doit reconstruire cette structure pour être identique aux existantes. — *vu sur 1 run (55-admin-selecteurs, Symfony)*

## 2026-06-11 — run un-moteur (projet avec API réelle authentifiée)
- **Credentials live = interdiction réseau dans CHAQUE brief, pas seulement le premier** : un devil's advocate a "testé" submit() avec un id bidon et a émis une vraie requête HTTP malgré l'interdiction générale. Depuis : chaque brief d'agent répète l'interdit, impose la vérification par LECTURE + tests mockés (tripwire assert_not_called), et mentionne l'incident. Aucune récidive sur 5 agents suivants.
- **Test de parité entre deux moteurs : comparer les SORTIES réelles des deux moteurs, jamais une ré-implémentation du pipeline dans le test** : l'agent B a écrit un helper qui rejouait le pipeline avec l'ANCIEN contrat → 3 faux échecs au gate. Le red-check par mutation a aussi attrapé 2 tests vacants (cap jamais exercé par le fixture) — muter la constante/le gate est le seul moyen de prouver qu'un test de cap mord.
